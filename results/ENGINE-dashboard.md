# Read-only live W&B board

`engine_dashboard.py` reads the existing EXP161 runtime-b6.json and mirrors scalar
metrics into two W&B runs in one project. It can attach AFTER training starts;
no training restart, source-code/hash migration, checkpoint changes or GPU memory
allocation by the observer is needed. W&B SDK lives in a separate small venv.

## Setup at the user's existing nested checkout

```bash
cd /data/workdir/_biometric-old/biometric-linking-guarded-v4/engine-core-src
git pull --ff-only
python3 -m venv ../engine-board-env
../engine-board-env/bin/python -m pip install -r requirements-dashboard.txt
../engine-board-env/bin/wandb login
```

Sign in to W&B in the browser and enter the requested W&B key in YOUR terminal,
not chat or Git. This creates/uses your account; no account was created or logged
in by the code preparation. No change to engine-core-env/JAX/CUDA is required.

```bash
RUN_DIR="$PWD/../engine-core"
nohup ../engine-board-env/bin/python -u -m engine_dashboard \
  --work-dir "$RUN_DIR" --project engine-core \
  > "$RUN_DIR/dashboard.log" 2>&1 &
```

If using a W&B team add `--entity YOUR_TEAM`; otherwise your default entity is
used. `--project` can be changed. Once authenticated, the observer prints actual
run links into dashboard.log and stores dashboard/links.json:

```bash
tail -n 20 ../engine-core/dashboard.log
cat ../engine-core/dashboard/links.json
```

Open either link and its project Workspace to compare the two named runs:
Wiki control / b6 and C4 fresh / b6. Scalar charts are generated by the SDK.
The links only become known after successful user-account initialization.

## Plots and interpretation

- validation/wiki_A/B/C_nll: historical reused Wiki validation panels.
- validation/c4_D_nll: same non-training C4 D128 panel across checkpoints.
- English stories/Russian Wiki NLL: metric names include16windows or128windows.
  Different panels are NOT connected into a fake matched learning curve.
- train/loss,ce,kl and gradient magnitude: training-batch values, distinct from
  held-out NLL. Initial execution-audit timing is excluded from throughput plots.
- performance/input_tokens_per_second: completed training-kernel update rate,
  not wall-clock end-to-end throughput including saves/evaluation.
- gpu memory/utilization/power/temperature: selected whole GPU, including the
  existing unrelated services. Not a per-model allocation or theoretical FLOPs.
- storage HF pending/error, raw report age and trainer_status in run summary.

Main learning-curve x-axis is new input tokens IN EXP161 (global-origin)*6*256,
not global optimizer-step*256, unique tokens, preparation cost or full lineage.
Each run gets its OWN token clock. BEST is summary only, not a second current
curve. LAST endpoints are shown. Reused/fresh panels remain diagnostic validation,
not newly untouched final tests. Sampling is limited by actual runner evaluations;
the watcher does NOT add forward passes or invent intermediate validation values.

## Reliability, resume and privacy

Poll15s; attach backfills existing history. Stable per-arm W&B IDs resume with
resume=allow, local per-point metric cursors prevent duplicate backfill and allow
late endpoint completion. A recorded state recovery starts a separate run segment
so old discarded-future points aren't presented as the resumed trajectory.
Explicit custom token axes permit late measurements while SDK history steps
increase normally. Raw runtime-b6.json remains the authoritative audit source.

Separate process means authentication/network/dashboard errors cannot stop or
change training. W&B journals metrics locally during network interruptions after
successful initialization. `--mode offline` records locally for later `wandb sync`;
offline mode does not produce a live cloud board. `--once` imports one snapshot.
WANDB0.31 resumes online run IDs; offline resume behavior is SDK-limited.

Console upload, code/Git capture, automatic system/host metadata/statistics and
optional SDK usage analytics are disabled. Only selected scalar metrics and small
whitelisted config are logged; no full report, environment dictionary, API keys,
weights, dataset samples or hidden states. W&B auth files follow SDK login behavior.

Files stay under WORK/dashboard and dashboard.log. No training lock is acquired:
on Linux /proc/locks is read to detect the owned trainer lock without racing a
new launch. After the matching final launcher status is saved AND its lock is
released, the observer syncs final metrics and finishes. Otherwise it keeps
watching. Ctrl+C/SIGTERM stops ONLY the observer; a stopped observer does not
imply the trainer stopped. Run summary trainer_status reflects the actual JSON.
One observer lock prevents duplicate uploads. No server firewall/port opening.

## Verification

Tests cover exact batch6 token axes, no historical BEST injection, distinct16/128
panels, repeated/late polling, stable resume and recovery segments. Real SDK0.31
offline smoke creates TWO simultaneously active runs and logs the extracted data.
These are not an authenticated online-board or live-server test; user login and
the server watcher startup are still required.

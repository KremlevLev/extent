# EXP-168: запуск и два вида остановки

Подготовлен31октября2026. Код и локальные тесты готовы; реальный168 не запускался.
Источник — завершённый EXP167 LR-x1 CURRENT185241, Adam30389, Edu window237441.
LR1e-5, нормы1e-6; расписание LR пока не меняется. Общий предел320M новых входов,
не повторяющийся при возобновлении. При конце данных сохранение и выход.

## Запуск / продолжение

После фактического завершения предыдущего процесса:

```bash
cd /data/workdir/_biometric-old/biometric-linking-guarded-v4/engine-core-src
git pull --ff-only
source ../engine-core-env/bin/activate
set -a
source ../engine-core.env
set +a
unset LD_LIBRARY_PATH
RUN_DIR="$PWD/../engine-core"
HOURS=48
nohup python -u -m engine_launch --runner long \
  --work-dir "$RUN_DIR" --max-wall-hours "$HOURS" \
  --leave-free-gib 5 --save-reserve-minutes 18 --clear-stop \
  >> "$RUN_DIR/runtime-long.log" 2>&1 &
tail -n 40 -f "$RUN_DIR/runtime-long.log"
```

HOURS — весь текущий запуск, с подготовкой600M потока, восстановлением и
сохранениями. Последующие9/5часов задаются новой той же командой с HOURS=9/5.
--pilot-updates156250 — неизменный общий горизонт168; не менять при resume.
Первый запуск сам строит data-pack-edu-600m. Старые data-pack-edu и валидация
не изменяются, SHA100M-префикса проверяется перед обучением. Пересборка читает
pinned источник заново, чтобы корректно сохранить хвост прежнего обрезанного
документа. Бинарные600M int32 занимают2.4GB, старые100M ещё0.4GB. Подготовка
возобновляется по журналу, без накопления временных Parquet-шардов.

## Быстрый локальный стоп

В ДРУГОЙ консоли с тем же окружением и загруженным engine-core.env:

```bash
cd /data/workdir/_biometric-old/biometric-linking-guarded-v4/engine-core-src
source ../engine-core-env/bin/activate
set -a
source ../engine-core.env
set +a
python -m engine_control --fast --work-dir "$PWD/../engine-core"
```

Обучение завершает безопасную границу, сохраняет только текущие q/Adam/курсор
локально без финальных оценок и без нового HF sync. Процесс выходит и освобождает
GPU; engine_control подтверждает это по завершению PID, затем отправляет уведомление.
Только появление FAST_STOP или локального файла отчёта не считается освобождением
GPU. Запись полного состояния порядка22GB всё равно необходима; конкретная
задержка зависит от SSD и текущей операции. Во время компиляции/уже начатой передачи
запрос может ждать её завершения. При таймауте контроллер НЕ сообщает успех.
Старые локальные поколения прунятся атомарным checkpoint store; после быстрого
стопа остаётся последнее нужное состояние, без отправки его на HF. Его нельзя
удалять вручную до обычного мягкого стопа. Данные переживают выход процесса,
но утрата локального диска до отправки HF потеряет неподтверждённый прогресс.

Продолжение — прежняя команда запуска с --clear-stop: загрузится собственный
CURRENT168, его моменты и следующий токен. Бот /check подцепляется автоматически.
Быстрый стоп реализован только для168; не применять к старому167 процессу.

## Обычный мягкий стоп и очистка states

```bash
touch /data/workdir/_biometric-old/biometric-linking-guarded-v4/engine-core/STOP
```

Оценки, локальное сохранение, попытка полного HF sync, затем проверка remote
commit-манифестов. После успешного sync **автоматически удаляются локальные
слоты states известных экспериментов161/163–168, совпавшие с удалёнными**.
При несовпадении/недоступности HF слот сохраняется и причина пишется в отчёт.
Неизвестные каталоги и симлинки не удаляются. Датасеты, код, секреты и чужие
процессы не затрагиваются. Это также действует при штатном завершении по времени/
токенам, но НИКОГДА при быстром локальном стопе. Лимиты:220GB рабочего каталога,
20GB свободного диска,128GB новых отправок за одну сессию. На длинном отрезке
HF sync каждые12ч и на выходе; передача синхронная и измеряется отдельно.

После очистки следующий запуск восстанавливает необходимые состояния с HF:
это экономит место, но повторное скачивание занимает время. Если есть свободное
место, быстрые паузы избегают этого обмена; обычный стоп освобождает states.

Итоговый отчёт results/runtime-long.json. В нём kernel throughput, принятые токены,
phase_seconds для обновлений/оценок/планировщика/сохранений/синхронизаций и остаток
unattributed_setup_io. Последний объединяет неизмеренные загрузки/сборку/прочее:
полного отдельного профиля каждой загрузки пока нет. Не выдавать kernel tok/s за
скорость всего запуска. Фазы относятся к одной invocation, счётчики токенов —
ко всей линии168. Cleanup подтверждается state_cleanup, а не просто pending=0.
